# ADR-001: v0 基准验证的范围与方法

- 日期：2026-08-20
- 状态：已接受
- 背景：机器人中间件架构（参考《两人中间件团队支撑产品线》构想）在冻结承诺前，需对两条最高风险链路做数据验证。

## 决策

v0 只测两条链路，不搭完整平台：

1. **机内通信链路**（触觉→控制方向）：rclcpp 串行 ping-pong 往返时延（RTT），跨进程（DDS）与进程内（intra-process 零拷贝）两种模式，载荷 1KB（触觉帧）/16KB（密集阵列）/1MB（图像块）。
2. **端云链路**（数采方向）：zenoh（Python 绑定）loopback 时延 + 持续灌流吞吐/丢帧。

## 方法

- 串行发-收（每收到回声才发下一帧）→ 测纯链路时延，不含排队。
- 每配置 warmup 300 帧；统计 P50/P90/P99/P999/max（µs）。
- 单向时延 = RTT/2（两进程各自打戳做钟差对齐不现实，ping-pong 两侧近似对称）。
- ping/pong 分别绑核（taskset core 2/4，zenoh 8/6），Release 构建。

## 环境与已知局限（重要）

- WSL2（12 核，21GB 内存），非实时内核，非目标硬件——**数字用于架构方向判断与相对比较，不作为最终性能承诺**。
- **FastDDS 稳定性观察**：首轮运行中 rmw_fastrtps_cpp 默认传输两度 discovery 超时（当时系统存在残留的旧 pong 进程）；清理后同配置复测成功。结论按「环境不稳定观察」记录，不作「WSL2 不可用」的定论；后续如复现再深挖。CycloneDDS 全程稳定。
- zenoh 走 Python 绑定：吞吐数字受 GIL/绑定开销压制，代表下界；时延数字含 Python 回调调度。
- zenoh 未做弱网模拟（WSL2 无 sudo 配 tc netem），loopback 只验证协议栈与序列化开销上界。

## 后果

- 1MB 级载荷跨进程 DDS 路径的实测数据直接决定图像/高密触觉流是否必须走进程内组合或 SHM/loaned 路径（见结果报告）。
- 本工程保留为可重跑的基准资产，换硬件后重跑即可刷新结论。
